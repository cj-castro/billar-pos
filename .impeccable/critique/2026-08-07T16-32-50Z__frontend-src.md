## Design Specificity Verdict

**LLM assessment (Assessment A):** This is genuinely authored for a billiard bar, not a reskinned generic POS. `ResourceCard` structurally distinguishes pool tables / regular tables / bar seats as different entity types, with only pool tables running a mono elapsed-time readout because only pool tables bill by time. `TicketPage.tsx`'s `livePoolCents` hand-rolls three billing modes (PER_MINUTE, ROUND_15, PER_HOUR) mirrored from the backend — a mechanic no restaurant POS needs. `WaitingListPanel.tsx` explicitly excludes pool tables from the general waitlist-assignment pool because pool tables are walked up to directly on the floor map, and it has a dedicated "SEATED → transfer to pool" two-stage queue mechanic that only exists because pool tables are a scarce, billed resource. Rappi delivery and "Venta Rápida" as first-class ticket types reflect real mixed order channels. The "¡RECUERDA DEVOLVER LA IDENTIFICACIÓN AL CLIENTE!" reminder on ticket close is a México-specific bar operational detail (ID held as collateral for cue/equipment) no generic template would include.

**Deterministic scan (Assessment B):** The mechanical detector returned 23 `gray-on-color` findings; verifying each against actual source revealed **17 are false positives** caused by the detector pairing background/text classes from opposite branches of a ternary — a known limitation from the prior harden pass on this branch. Of the remaining 6 correctly-paired findings, computing real WCAG contrast confirms 5 pass comfortably (5.6–8.3:1 — dark `slate-900` text on mid-bright amber/yellow fills, which reads fine despite the detector's generic "gray text" heuristic firing on it). **One genuine, previously-missed issue surfaced**: `TicketPage.tsx:757` — the hover state `hover:bg-green-700` combined with resting `text-slate-200` computes to **~4.07:1**, just under the 4.5:1 AA floor. This is the same failure *shape* as `TableManagementPage.tsx:221`, which the prior harden pass already fixed — this sibling instance was missed.

Beyond contrast, Assessment B's broader grep sweep found: ARIA coverage is 2 of 31 `.tsx` files (both already fixed for keyboard access in the prior harden pass; the other 29 files carry zero `aria-`/`role` attributes, though most of their interactive elements are native `<button>`s, which don't need them); 6 inline `style={{}}` usages (all legitimate — dynamic chart colors, computed widths, not token-system bypasses); and **14 files independently hand-roll near-identical modal-overlay markup** (`fixed inset-0 bg-black/… flex items-end sm:items-center …`) with no shared `Modal` component — real, uncontested duplication past the 3-use extraction threshold.

**Visual overlays**: unavailable — no browser automation tool is exposed in this session, and no dev server was running. CLI/source-level scan only; no user-visible overlay to point to.

## Overall Impression

The app earns its identity — this doesn't read as a generic POS with a dark theme slapped on, it reads as software built by someone who understands how a specific bar runs its floor. The gap between the app's best flow (`AddItemModal`'s staged wizard) and its weakest (the unstaged payment modal, and the manager reports/inventory density) is the single biggest opportunity: the design language that works is proven inside the app itself, it just isn't applied consistently to the other high-stakes and high-density screens.

## What's Working

1. **`AddItemModal.tsx`'s staged wizard** (category → items → modifiers → confirm) with a live completeness counter and a "✓ Listo" early-exit shortcut. It prevents incomplete orders, shows exactly what's left, and respects a rushed waiter's time — this is the app's best-designed flow and should be the template for the others.
2. **`ResourceCard.tsx`'s single-glance state encoding.** Color, border weight, the pulse on in-use tables, and the conditional customer-name/timer/waiting-badge stack deliver on DESIGN.md's "readable from three feet away" principle. The `locked` (bar-closed) state reusing the same visual grammar rather than inventing a new one is a good consistency call.
3. **The WAC restock preview in `InventoryPage.tsx`** — showing "new WAC: $X/unit" before a manager commits a restock answers "did I just mess up my cost basis" before the action lands, exactly the trust-surface support PRODUCT.md's money-correctness principle calls for.

## Priority Issues

**[P1] Payment modal carries too much simultaneous state for the app's single highest-stakes interaction**
- **Why it matters:** `TicketPage.tsx` (lines 1002-1291) keeps payment type, split toggle, tip mode/source/split-amounts, and tendered amount all live and recalculating at once, with no staged review step before charging. The split tip-source sub-flow asks the waiter to manually reconcile two dollar amounts against a total — a math task under time pressure, on the one screen where a mistake costs real money.
- **Fix:** Collapse to a 2-step flow — configure (current form) → review & confirm (static summary, one tap to charge) — mirroring the pattern that already works well in `AddItemModal`'s confirm step.
- **Suggested command:** `/impeccable clarify` or `/impeccable onboard` (flow restructuring), then `/impeccable polish`

**[P2] English copy leaks into an otherwise fully Spanish, i18n-driven UI**
- **Why it matters:** `ManagerDashboard.tsx` tile descriptions mix untranslated English ("Open/close bar, tips, expenses", "Manage staff accounts") into Spanish sibling tiles; `WaitingListPanel.tsx`'s heading is "⏳ Waiting List" while every sibling section header on the same page is Spanish. For a Spanish-first waiter under time pressure, hitting an English label mid-scan breaks the "readable at a glance" premise the whole system depends on.
- **Fix:** Route every string in these two files through the `t()` i18n system already used elsewhere in the same files.
- **Suggested command:** `/impeccable clarify`

**[P2] 14 files hand-roll duplicate modal-overlay markup with no shared component**
- **Why it matters:** Confirmed by Assessment B's grep sweep — every future modal risks silently diverging (padding, backdrop opacity, breakpoint behavior already vary slightly across the 14 instances found). This is exactly the kind of drift a design system prevents by construction, and it compounds every time a new modal is added.
- **Fix:** Extract a shared `<Modal>` wrapper component carrying the backdrop, entry-position (bottom-sheet mobile / centered desktop), and `rounded-2xl`/`shadow-2xl` treatment already documented in DESIGN.md's Components section; migrate the 14 call sites.
- **Suggested command:** `/impeccable extract`

**[P3] Manager/reports surfaces trade hierarchy for raw density with no interpretive layer**
- **Why it matters:** `ReportsPage.tsx`'s 11 flat, ungrouped tabs and `InventoryPage.tsx`'s 6-8 icon-only action buttons per row ask a tired manager to parse rather than be told. DESIGN.md explicitly allows back-office screens to "lean into desktop density" — it does not say abandon hierarchy. Nothing in Reports summarizes "here's what matters today"; every tab is a raw table the manager must read and mentally total.
- **Fix:** Group the 11 report tabs into 3-4 logical clusters (Sales & Payments / Operations & Staff / Waste & Deletions / Charts); collapse Inventory's icon row behind a single overflow menu for the least-frequent actions so the primary action (restock) reads as primary.
- **Suggested command:** `/impeccable layout`

**[P3] The void flow loses context across three sequential modals**
- **Why it matters:** `TicketPage.tsx`'s void quantity picker → `ManagerPinDialog` → void reason modal are three separate full-screen overlays with no restatement of what's being voided. A manager entering their PIN three modals deep has no visual anchor confirming they're about to void the right thing.
- **Fix:** Carry a one-line summary ("Anulando: 2× Cerveza Corona") into both the PIN dialog and the reason modal.
- **Suggested command:** `/impeccable clarify`

## Persona Red Flags

**Alex (power user) opening a table and adding 5 items fast.** No cross-category quick-repeat exists — after item #1, `AddItemModal` resets cleanly to the items step within the same category (good), but an item in a *different* category forces Alex all the way back to the category grid. For 5 items spanning categories, that's 5 full category→item(→modifier)→confirm traversals with no recent-items shelf or cross-category shortcut.

**Casey (distracted mobile user) checking the kitchen queue one-handed.** The mobile tab switcher and full-width action buttons are genuinely thumb-friendly. But the print-retry icon (🖨️, top-right of each card, next to a timestamp) — the control for a real failure state (`needs_reprint`) — is small and easy to mis-tap or miss while holding a phone one-handed, worse-positioned than the primary status button gets for a lower-frequency but higher-consequence action.

**Riley (stress tester) with a very long customer name.** `ResourceCard.tsx` truncates the floor-card name safely (`truncate max-w-[110px]`), but `WaitingListPanel.tsx`'s free-text `party_name` input has no `maxLength` and no equivalent truncation guard on the waitlist row — a sufficiently long name could wrap awkwardly, though the row's flex-wrap layout provides some graceful degradation.

## Minor Observations

- `formatDistanceToNow`-style relative timestamps on kitchen/bar queue cards should be verified as actually localizing to Spanish ("hace 5 minutos") rather than defaulting to English, given everything else in the app is localized.
- `PromotionsPage.tsx`'s live preview panel is a strong, underused pattern — applying the same live-preview treatment to the discount and tip flows in `TicketPage.tsx` would reinforce the same design language.
- `InventoryPage.tsx` uses Tailwind dynamic class interpolation (`` `bg-${color}-700 border-${color}-600` ``) for adjust-type buttons — fragile under Tailwind's JIT purge since dynamic class names aren't statically analyzable; worth confirming these exact classes appear verbatim elsewhere or safelisting them.
- ARIA coverage is 2/31 `.tsx` files (both already patched for keyboard access in the prior harden pass) — confirms Assessment A's read that accessibility was "patched in reactively rather than systemically" rather than being a baseline habit.

## Questions to Consider

1. If the void flow and payment flow both exist to protect money-correctness (PRODUCT.md's own stated principle), why does one get careful multi-modal staging while the other collapses everything into a single scrolling form — should every money-touching action share one consistent interaction pattern?
2. The floor map has no acknowledgment of "quiet vs. broken" — an all-green, all-quiet floor reads identically whether it's a slow Tuesday or a stalled socket connection. What would one glance of reassurance look like there?
3. Given `AddItemModal`'s staged, one-decision-at-a-time discipline is the app's best-designed flow, what would it take to extend that same discipline to the payment modal and the Reports screen, both of which currently ask the user to hold many concurrent variables in view at once?
