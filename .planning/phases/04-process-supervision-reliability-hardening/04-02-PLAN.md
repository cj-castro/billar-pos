<objective>
Verify and restore DATA-03's eventlet single-worker constraint under the native Windows Services hosting model, closing a real gap: gunicorn's `--worker-class eventlet` used to call `eventlet.monkey_patch()` implicitly inside `EventletWorker.init_process()`, but Phase 2's native entrypoints (`backend/wsgi.py`, `backend/service_entry.py`) call `socketio.run()` directly with no gunicorn in between — so that implicit patching never happens today, and `psycopg2` (a blocking C-extension database driver) was never cooperatively patched even under Docker.

Purpose: Without this, every blocking Postgres call in the single eventlet OS thread stalls the entire hub — no other request, WebSocket keepalive, or background greenlet can run until that call returns. This directly threatens the single-worker/no-thread architecture invariant CLAUDE.md documents and DATA-03 requires be "explicitly verified... to still hold" under the new hosting model.

Output: `eventlet.monkey_patch()` + `psycopg2_patcher.make_psycopg_green()` as the first lines of both native entrypoints; a grep-audit confirming zero raw `threading.Thread` usage; an updated CLAUDE.md architecture note; a DATA-03 verification document.
</objective>

<interfaces>
`eventlet.support.psycopg2_patcher.make_psycopg_green()` (eventlet 0.36.1, already a pinned dependency in `backend/requirements.txt`): registers `psycopg2.extensions.set_wait_callback(...)` so psycopg2's blocking C-level socket I/O yields to eventlet's hub via `trampoline()` instead of blocking the OS thread. This is a SEPARATE, explicit call from `eventlet.monkey_patch()` — the plain `monkey_patch()` call does NOT patch psycopg2 on its own. Import as `from eventlet.support import psycopg2_patcher` then call `psycopg2_patcher.make_psycopg_green()`. Both calls (`eventlet.monkey_patch()` and `psycopg2_patcher.make_psycopg_green()`) must run before `psycopg2`/`sqlalchemy`/the Flask `app` package are imported anywhere in the process, per eventlet's documented usage pattern.

Existing established pattern this preserves (`backend/app/api/tickets.py` lines 32-86, `_spawn_auto_print_chit`): background work spawns via `socketio.start_background_task(_run)`, explicitly NOT `threading.Thread`, with an inline comment already explaining why. This plan's grep-audit confirms this remains the only spawning mechanism anywhere in `backend/`.
</interfaces>
