<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Public/LAN client → `GET /api/v1/health` | Unauthenticated endpoint, response body is directly attacker-visible |
| Backend process → print agent (`localhost:9191`) | Outbound call to a LAN service, URL sourced from a trusted env var, not user input |
| Application writes → `tickets`/`resources` tables | Trusted internal application code paths; the new triggers are a backstop, not a new input-validation boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Information Disclosure | `/api/v1/health` error response | mitigate | Failure branch returns only `type(e).__name__` in a generic "Database unreachable" message — never the raw exception string, `SQLALCHEMY_DATABASE_URI`, or connection details (ASVS V13). |
| T-04-02 | Denial of Service | `/api/v1/health` is unauthenticated and could be hit repeatedly | accept | Existing global Flask-Limiter config already applies to all `/api/*` routes; the added work per call is a single `SELECT 1`, not an unbounded resource; accepted at ASVS L1. |
| T-04-03 | Denial of Service | Print-agent reachability check adds a blocking HTTP call to backend startup | mitigate | Hard 3-second `timeout` on the `requests.get` call, wrapped in a catch-all try/except, never blocks indefinitely — matches D-13's warn-never-block requirement. |
| T-04-04 | Tampering | The ghost-ticket invariant triggers could theoretically be bypassed by a direct SQL write outside the application | accept | Postgres is only reachable from the local machine (native Windows service, not exposed externally per Phase 2 SVC-02); bypassing triggers additionally requires superuser `session_replication_role=replica`, out of scope for this phase's network boundary. |
| T-04-05 | Repudiation | A raised `fn_check_ticket_resource_consistency` exception surfaces as a raw Postgres error at `db.session.commit()`, with no existing try/except around most ticket-mutation commits | mitigate | The `RAISE EXCEPTION` message text explicitly includes `ghost-ticket invariant violated` plus the violating row count, so the resulting backend log entry is immediately diagnosable rather than a bare constraint-name error. |

Severity note: no HIGH-severity threat introduced; all new surface area is either read-only (health check), outbound-only with a bounded timeout (print-agent check), or a fail-closed DB-level invariant that only fires on already-invalid application state.
</threat_model>
