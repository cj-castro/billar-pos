This plan depends on every artifact created in Plans 01-04:
- scripts/install-postgres-native.ps1 — writes discovered service name to scripts\.postgres-service-name.txt (Plan 04)
- scripts/postgres-backup-restore.ps1 — exposes New-SyntheticSourceBackup, Restore-NativePostgres, Test-RestoredData (Plan 04)

- scripts/install-nssm-nginx.ps1 — registers BilliardBarNginx, deploys frontend\dist (Plan 03)

NSSM dependency syntax (02-RESEARCH.md Pattern 6): `nssm set <Service> DependOnService <other_service_name> [<other_service_name2>...]`. The Windows Service Control Manager honors this ordering on boot but does NOT guarantee the dependency is actually ready to accept connections (Pitfall #5/#2) — this plan relies on each downstream service's own connection-retry behavior for that gap, consistent with 02-RESEARCH.md's Pattern 6 recommendation to defer formal readiness health-checks to Phase 4.

ROADMAP.md Phase 2 Success Criteria (the four claims this plan's checkpoint must gather direct evidence for):
  1. A verified Postgres backup exists and has been restore-tested before any Postgres data migration begins (scoped to synthetic procedure per D-10)
  2. Flask/eventlet backend, PostgreSQL 15, and the React frontend all run as native Windows processes/services, with no Docker dependency
  3. The scheduler and Telegram bot run as their own independent native Windows services, decoupled from backend crashes
  4. Backend reaches the Windows print agent via localhost, with no remaining host.docker.internal references

| Threat ID | Category | Component | Disposition | Mitigation Plan |
