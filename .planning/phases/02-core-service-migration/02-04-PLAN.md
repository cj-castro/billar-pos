<objective>
Install PostgreSQL 15 as a native Windows service, hardened against the two most concrete Windows-native Postgres risks (auth method, network exposure), and prove the Docker-to-native logical dump/restore procedure works end-to-end using synthetic seed data (SVC-02, DATA-01 procedure per D-08/D-09/D-10).

Output: `scripts/install-postgres-native.ps1` (native install + hardening) and `scripts/postgres-backup-restore.ps1` (dump/restore/verify procedure, reusable unchanged in Phase 5 against real data).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Native Postgres service ↔ LAN network interface | Postgres binds to a real NIC on native Windows (unlike Docker, where it was never port-mapped to the host at all) — this is a NEW exposure surface relative to the current Docker setup |
| install-postgres-native.ps1 → Chocolatey / EnterpriseDB installer (internet download) | Supply-chain trust: fetching a database engine binary over the internet at install time |
| scripts\backups\*.dump on local disk | Contains a full logical copy of the database (synthetic-only in this phase per D-09) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-13 | Information Disclosure / Elevation of Privilege | Native Postgres reachable from the LAN (unlike Docker, which never exposed a host port for Postgres) | mitigate (HIGH) | `listen_addresses = 'localhost'` is explicitly set in postgresql.conf and NO firewall rule is opened for port 5432 — Postgres remains reachable only from the machine itself, matching (and in fact preserving) the current Docker deployment's total non-exposure of this port. |
| T-02-14 | Spoofing / Tampering | pg_hba.conf using `trust` authentication for local/host connections | mitigate (HIGH) | Script explicitly verifies and replaces any `trust` auth method with `scram-sha-256` (PostgreSQL 15's own modern default) before considering the install complete — prevents any local process from connecting to the database without a password. |
| T-02-15 | Information Disclosure | Postgres superuser password | mitigate | Generated randomly at script-run time via `Get-Random`, never hardcoded into the committed `.ps1` file, never logged to stdout. |
| T-02-16 | Tampering | install-postgres-native.ps1 (Chocolatey / EnterpriseDB installer download) | mitigate | Chocolatey is a widely-trusted Windows package manager (already used as the primary fallback for NSSM in the production print-agent script); the EnterpriseDB fallback downloads only from the official `get.enterprisedb.com` domain with a pinned version, not a "latest" scrape. |
| T-02-17 | Information Disclosure | scripts\backups\billiardbar_staging.dump (synthetic seed data only, per D-09) | accept | Contains zero real customer/business data (D-09 explicitly restricts Phase 2 to synthetic `seed.py` data) — low consequence if disclosed. Real-data backup access-control is explicitly a Phase 5 concern, noted in the script's own comments, not silently dropped. |

Severity note: Two HIGH-severity items are identified (T-02-13 network exposure, T-02-14 weak auth) — both are explicitly mitigated by concrete configuration changes in Task 1, satisfying the ASVS L1 block-on-unmitigated-HIGH requirement.
</threat_model>
