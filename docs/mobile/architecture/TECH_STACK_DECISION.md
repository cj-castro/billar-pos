# Tech Stack Decision - Mobile POS Companion

Status: Accepted (elaborates D1, D2, D11, D12). Versions checked against the npm registry on 2026-11-05. Re-run `npx expo install --check` before scaffolding; Expo's `bundledNativeModules.json` for the SDK is the version authority for native modules.

## 1. Problem and constraints

Staff phones (Android first, iOS later) must talk to an existing Flask + Socket.IO + Postgres POS over a bar LAN (`http://<host>:8080`). Constraints that drive the choice:

- The web stack is React 18 / TypeScript / zustand / TanStack Query 5 / axios / socket.io-client 4.8 / i18next 26 with `es`/`en` object literals. Reuse of *logic* (not DOM UI) is the biggest cost saver.
- Windows build host: JDK 21 present, Android SDK present, **no Android Studio**. Everything must build from the command line (Gradle). No Mac now; iOS comes later.
- D2: no EAS cloud, no store publishing. Sideloaded APK.
- LAN HTTP (cleartext) and long-lived WebSocket are required.
- Small team, so maintainability beats peak performance. The screens are lists, forms and status chips; none are graphics heavy.

## 2. Options evaluated

| Option | Summary | Main strength | Main weakness |
|---|---|---|---|
| A. Expo (React Native, TS, prebuild/CNG) | RN with Expo SDK 58, Expo Router, local `expo prebuild` + Gradle | Reuses TS logic, libs and i18n; one codebase; Expo modules (SecureStore, build-properties) handle native config | Native layer is generated; RN upgrades each SDK; needs a Mac for iOS later |
| B. Bare React Native | RN CLI template, hand-managed `android/` and `ios/` | Full native control | Hand-maintains what CNG gives free (manifest, Gradle glue); no gain for this app |
| C. Flutter | Dart, Impeller | Excellent UI perf, strong tooling | Zero reuse (Dart): rewrite client, state, i18n, socket handling; second language |
| D. Kotlin Multiplatform + Compose MP | Shared Kotlin, Compose UI on both | Native-quality, typed | Zero reuse; Compose for iOS younger; iOS still needs Xcode; bigger skill ask |
| E. Native Kotlin + Swift | Two apps | Best platform fit | Two codebases for a small effort; zero reuse; iOS is a full second build |
| F. Capacitor / PWA | Wrap the existing Vite web app in a WebView | Maximum code reuse, including UI | Web UI is desktop-first; WebView cleartext and mixed-content limits; no native secure storage without plugins; worse KDS ergonomics; same background-socket limits as native |

## 3. Weighted scoring (1 = poor, 5 = excellent)

| Criterion | Weight | A Expo | B Bare RN | C Flutter | D KMP/CMP | E Native | F Capacitor |
|---|---:|---:|---:|---:|---:|---:|---:|
| Repo compatibility (TS/React/TanStack/zustand/i18next reuse) | 20 | 5 | 5 | 1 | 1 | 1 | 5 |
| Android workflow on this Windows host (JDK 21, SDK, no Studio) | 15 | 4 | 4 | 4 | 4 | 5 | 4 |
| iOS later on a Mac | 10 | 4 | 4 | 4 | 3 | 1 | 4 |
| UI performance | 10 | 4 | 4 | 5 | 4 | 5 | 3 |
| LAN / WebSocket / cleartext support | 10 | 4 | 4 | 4 | 4 | 5 | 3 |
| Testing story (unit, component, E2E) | 10 | 4 | 4 | 4 | 3 | 4 | 4 |
| Maintainability (one language, one codebase, team fit) | 15 | 5 | 3 | 3 | 2 | 1 | 4 |
| Build complexity / moving parts | 10 | 4 | 3 | 3 | 2 | 3 | 4 |
| **Weighted total (of 100)** | 100 | **87** | 79 | 65 | 54 | 58 | 80 |

Computation: sum(weight x score) / 5. Expo: (20x5 + 15x4 + 10x4 + 10x4 + 10x4 + 10x4 + 15x5 + 10x4) / 5 = 435 / 5 = 87.

Reading the table:
- Capacitor (80) is the closest competitor because it reuses everything. It loses on what matters to a phone-first staff tool: native secure token storage, cleartext/mixed-content behaviour in a WebView, and list/gesture ergonomics for the KDS. The web UI would also need a mobile redesign anyway (the design workstream produces one), so UI reuse is worth less than the table credits.
- Bare RN is Expo minus the generated native config. No requirement here needs hand-edited native code.
- Scores are judgement, not measurement. Expo stays first unless repo-compat is weighted below roughly 10, which would contradict the project's premise.

**Decision: Expo (React Native) + TypeScript (D1).**

## 4. Build model (D2: local only)

- `mobile/` is an Expo app. `android/` and `ios/` are **generated by `npx expo prebuild` and git-ignored** (continuous native generation). All native configuration lives in `app.json` and config plugins, so it is reviewable and reproducible.
- Debug: `npx expo run:android` (Gradle `assembleDebug`, installs to emulator `billar_mobile_api35` or a USB phone; Metro serves JS). Release: `cd android && gradlew assembleRelease`, signed with a **local** keystore that is never committed.
- **Not used:** `eas-cli`, `eas.json`, `expo-updates` (OTA depends on EAS Update), `expo-dev-client` (debug builds load from Metro), Expo Go (cannot carry our build-properties config).
- Host notes: Node 24 is installed (SDK 58 requires `^22.13 || ^24.3`). Enable Windows long paths (`LongPathsEnabled=1`) and keep the worktree path short; New Architecture CMake builds hit the 260-character limit otherwise. The Android SDK needs `cmdline-tools`, `platform-tools`, the platform and build-tools versions the SDK template requires, and `ANDROID_HOME`. Exact steps belong to `LOCAL_DEV_ENVIRONMENT.md` (DevOps workstream).
- iOS later: `expo prebuild --platform ios` on a Mac plus Xcode; no code changes expected beyond section 8.

## 6. Cleartext HTTP on Android (risk)

Since Android 9 (API 28), apps targeting API 28+ block cleartext HTTP by default. The LAN backend is `http://`, so a release build would fail every request with "Cleartext HTTP traffic not permitted" even though debug builds pass (Metro already needs cleartext in debug).

Decision: enable it through the config plugin, not a hand-edited manifest, so it survives `prebuild`:

```jsonc
// mobile/app.json (excerpt)
["expo-build-properties", { "android": { "usesCleartextTraffic": true } }]
```

Why global rather than a scoped `network_security_config.xml`: the server URL is entered by the user, and Android network security config scopes cleartext only to named domains or literal IPs, not CIDR ranges. A per-IP file would force a rebuild whenever the bar's IP changes.

Mitigations in app code (defence in depth, not a security boundary):
1. Server-URL validation refuses `http://` to non-private hosts. Allowed: RFC1918 (`10/8`, `172.16/12`, `192.168/16`), `169.254/16`, `localhost`, `10.0.2.2`, `*.local`, single-label hostnames. Public hosts must be `https://`.
2. No third-party SDKs and no analytics, so no secondary cleartext calls.

Risk: anyone on the same Wi-Fi can read tokens and order data and can replay a sniffed refresh token for up to 7 days (G3). Full model and roadmap are in `SECURITY_MODEL.md`.

Future HTTPS path (no app rewrite; the base URL is already configurable):
1. Reverse proxy or nginx terminates TLS on the POS host with a certificate for a real domain that resolves to the LAN IP (DNS-01 challenge, nothing exposed inbound). Preferred; phones need no CA install.
2. Local CA (mkcert or step-ca) installed on phones. Android also needs a network security config that trusts user CAs.
3. Self-signed certificate with pinning in the app.

When HTTPS lands: set `usesCleartextTraffic` to false and tighten the URL validator to `https://` only. iOS later: ATS `NSAllowsLocalNetworking` permits local HTTP without disabling ATS globally, plus `NSLocalNetworkUsageDescription`.

## 7. Testing stack

| Level | Tooling | Scope |
|---|---|---|
| Unit | jest-expo | repositories, error normalizer, retry logic, draft reducer, money/time helpers, socket-event mapper |
| Component/integration | RN Testing Library + mock repository adapter | role-based screens, disabled/duplicate-tap behaviour, offline banner states |
| Contract | Jest `node` project against the real local backend (`http://localhost:8090`) | see INTEGRATION_STRATEGY |
| E2E | Maestro flows on `billar_mobile_api35` against `10.0.2.2:8090` | login per role, open ticket, add and send, KDS ready, offline banner |

If Maestro will not run on Windows (needs JDK and adb on PATH; verify first), fall back to an `adb`-driven smoke script plus screenshot capture, with component tests carrying most of the weight. Decide after the DevOps workstream reports.

## 8. iOS-readiness rules

No Android-only JS APIs outside `Platform.select`; no hand edits in `android/` (generated); SecureStore, NetInfo and AsyncStorage are cross-platform; safe areas via `react-native-safe-area-context`; ATS and local-network keys through `app.json` `ios.infoPlist`. iOS cannot be built or tested on this host and stays unverified until a Mac is available.

## 9. Source layout

Conventional Expo Router layout; the Mobile App Builder scaffolds the same tree.

```
mobile/
  app.json                      # expo config + plugins (expo-router, expo-secure-store, expo-build-properties)
  package.json  tsconfig.json  babel.config.js  jest.config.js  metro.config.js
  .gitignore                    # android/ ios/ .expo/ *.keystore
  app/                          # expo-router routes only; thin, no business logic
    _layout.tsx                 # providers: QueryClient+persist, RepositoryProvider, i18n, Socket, ConnectionBanner
    index.tsx                   # boot gate: serverUrl? session? -> redirect by role (D9)
    server-setup.tsx            # URL entry + /health validation (D8)
    (auth)/login.tsx
    access-denied.tsx           # unknown role (D9)
    (waiter)/                   # WAITER
      _layout.tsx               # role guard (redirect on role mismatch)
      floor.tsx
      ticket/[id].tsx
      ticket/[id]/add-item.tsx
    (kds)/[station].tsx         # KITCHEN_STAFF -> kitchen, BAR_STAFF -> bar (manager may view)
    (manager)/                  # MANAGER, ADMIN
      _layout.tsx
      ops.tsx
    (admin)/diagnostics.tsx     # ADMIN
  src/
    api/                        # axios client, interceptors, endpoint functions, error normalizer, health
    repositories/               # real adapter (default) + mock/ (demo and tests only); the D13 seam
    state/                      # zustand: authStore, draftStore, connectionStore, settingsStore
    domain/                     # types mirroring backend to_dict() shapes (snake_case), enums, role helpers
    realtime/                   # socket client, room manager, event -> invalidation map, ready-notification handler
    i18n/                       # init + es.ts/en.ts copied from web (a test asserts key parity with web)
    theme/                      # tokens from web palette (slate surfaces, sky accent), typography, spacing
    components/                 # shared presentational: Button, StatusChip, StaleBadge, Banner, PinDialog
    features/<feature>/         # auth, floor, ticket, order-draft, kds, manager, admin, connection
      components/  hooks/
    utils/                      # money (formatMXN), time (useTimer), uuid, logger (redacting)
    test/                       # fixtures, render helpers, contract/ (jest node project), maestro/ flows
```

Dependency direction: `app/` imports `src/features/*`; features reach the backend only through hooks over `repositories`, never `api/` directly; `repositories` import `api/` and `domain/`; `domain/` imports nothing. Domain types stay snake_case as sent on the wire; there is no camelCase mapping layer (it would add code and drift risk for no behavioural gain).

## 10. Consequences and reversibility

- Easier: one TS codebase, ported client/socket/i18n logic, reproducible local builds, iOS via prebuild later.
- Harder: RN upgrade cadence (stay on SDK 58 until there is a reason to move); generated native code means native issues need `prebuild --clean`; Hermes `Intl` gaps need tests.
- Reversibility: medium. Domain types, API layer, repositories and tests are framework-agnostic TS; only `app/`, `components/` and `features/**/components` are RN. Moving to bare RN means no longer regenerating `android/`. Moving to Capacitor or native reuses the contract tests and backend extensions unchanged.
